# เล่าเรื่องโครงงาน — Thai Flood Causal-Chain GraphRAG

> เอกสารนี้เขียนแบบ "เล่าเรื่อง" สำหรับนำไปเล่าให้อาจารย์ที่ปรึกษาฟัง
> ไล่ตั้งแต่ *ทำไมถึงเริ่ม → เทียบอะไรกับอะไร → ทำไมเป็นน้ำท่วม → ได้ผลยังไง → ต่อยอดอะไรไปแล้ว*

---

## 1. จุดเริ่ม — เราไม่พอใจกับ "hop count" แบบเดิม

ตอนนี้งาน GraphRAG ส่วนใหญ่ เวลาจะบอกว่า *"กราฟช่วยให้ตอบคำถามหลายขั้น (multi-hop) ได้ดีกว่า vector search"*
เขาวัดกันด้วย hop ที่เป็น **ความสัมพันธ์เชิงข้อมูล (entity-relation)** เช่น
*มัสยิด → อยู่ในจังหวัด → มีที่พัก* — คือการเดินจากของหนึ่งไปอีกของหนึ่งเพราะมัน "เกี่ยวข้องกัน"

คำถามที่เราตั้งคือ — **แล้วถ้า hop นั้นไม่ใช่แค่ "เกี่ยวข้องกัน" แต่เป็นสายเหตุ-ผลจริงในธรรมชาติล่ะ?**
มันจะยากขึ้นสำหรับ GraphRAG ในอัตราเดียวกันไหม? อันนี้ยังไม่มีใครวัด เพราะ **causal ≠ relational** —
การเดินตามเหตุที่ทำให้เกิดผลจริง มันบังคับให้ทุกก้าวต้อง "อธิบายได้ว่าทำไม" ไม่ใช่แค่ "มันต่อกันอยู่"

---

## 2. ทำไมต้องเป็นน้ำท่วม

เราต้องหา domain ที่ **สายเหตุ-ผลชัดและวัดได้จริง** ไม่ใช่เหตุผลลอย ๆ
น้ำท่วมลุ่มเจ้าพระยาตอบโจทย์นี้เป๊ะ เพราะสายมันเป็นฟิสิกส์ล้วน ๆ:

> **ฝนตกต้นน้ำ → น้ำเข้าเขื่อน → เขื่อนล้นสปิลเวย์ → ระดับแม่น้ำท้ายน้ำสูงขึ้น → จังหวัดปลายน้ำท่วม**

ข้อดีคือทุกก้าวในสายนี้ **มีข้อมูลจริงมายืนยันได้**:
- สถานีวัดฝนต้นน้ำ
- ระดับน้ำเขื่อน
- เกจวัดระดับแม่น้ำ (กรมชลประทาน / RID)
- และที่สำคัญ **ภาพถ่ายดาวเทียม GISTDA บอกว่าจังหวัดไหนท่วมจริง** → ใช้เป็น "เฉลย (ground truth)"

เลือกน้ำท่วม **ไม่ใช่เพราะเป็นประเด็นร้อน** แต่เพราะมันเป็น **สายเหตุ-ผลที่ตรวจสอบย้อนได้ทุกก้าว**

---

## 3. เราเทียบอะไรกับอะไร

สร้างระบบ 3 ตัวให้ตอบคำถามเดียวกัน — *"ทำไมจังหวัดนี้ถึงน้ำท่วม?"* — บนชุดข้อสอบเดียวกัน:

| ระบบ | มันคิดยังไง |
|---|---|
| **Causal-GraphRAG** (ของเรา) | เดินตามสายเหตุ-ผลจริงในกราฟ Neo4j: ฝน→เขื่อน→แม่น้ำ→จังหวัด |
| **Entity-GraphRAG** (baseline) | เดินกราฟเหมือนกัน แต่ตามความ "อยู่ใกล้/เกี่ยวข้อง" ไม่สนทิศทางการไหล |
| **Vector-RAG** (baseline) | ไม่มีกราฟ — ค้นจากข้อความรายงานข่าวน้ำท่วมด้วยความคล้ายของข้อความ |

**สมมติฐานหลัก 2 ข้อ:**
- **H1** — ระบบที่เดินตามเหตุ-ผลจริงจะให้คำตอบที่ *ตรวจสอบย้อนกลับไปหาหลักฐานได้* (traceable) มากกว่า
- **H2** — F1 ของ GraphRAG จะ *ไม่ตก* ตามความยาวสายเหตุ-ผลเร็วเท่า vector search (กราฟทน hop ได้ดีกว่า)

**หัวใจของความยุติธรรม:** เฉลยมาจากดาวเทียม GISTDA ที่เป็น *อิสระจากตัวโมเดล* — โมเดลไม่เคยเห็นเฉลย
และเราตัดวงจร (de-circularize) ด้วยการให้ "ประตูน้ำล้น" ตัดสินจากเกจวัดแม่น้ำจริงของกรมชล
**ไม่ใช่จากดาวเทียมที่เป็นเฉลย** เพื่อไม่ให้เป็นการโกงตัวเอง

---

## 4. ผลออกมายังไง (เล่าตามจริง — มีทั้งชนะและแพ้)

**สิ่งที่ causal ชนะขาด — และเป็นหัวใจของงาน (H1):**
- **Traceability** และ **Specificity**: causal ทำได้จริง ส่วน baseline ทั้งสองตัว = **0**
  → baseline ตอบได้ว่า "ท่วม" แต่ **ชี้กลับไปว่าเพราะเขื่อนไหน สายน้ำไหนไม่ได้เลย**
  ส่วนของเราชี้ได้ทุกก้าวพร้อมหลักฐาน (สถานี/timestamp)

**เรื่อง F1 (ความแม่นในการทายว่าจังหวัดไหนท่วม):**
- ทดสอบจริง 4 เหตุการณ์ (ปี 2022, 2021, 2024, 2023 รวม **92 เคส**)
- causal ดีกว่า entity อย่างมีนัยสำคัญแบบ **one-sided (p=0.044)** ส่วน two-sided ยังไม่ผ่าน (p=0.087)
  → **รายงานตรง ๆ ทั้งสองค่า ไม่เลือกเฉพาะตัวที่สวย**
- เทียบกับ vector-RAG ชนะขาด (p<0.001)
- **จุดที่แพ้และไม่ปิดบัง**: ปี 2024 causal พลาด เพราะ "ประตูน้ำล้น" ตั้งเป็นเกณฑ์ตายตัว
  → เป็นข้อจำกัดจริงที่บันทึกไว้ในเอกสาร ไม่ได้ไปแก้เฉลยหรือจูนให้ดูดี

**บทเรียนสำคัญที่สุด** — ตอนแรกตอนมีเหตุการณ์เดียว F1 ได้ **1.000** ดูสวยเกินจริง
พอขยายเป็นทั้งลุ่มน้ำ 23 จังหวัด มัน **ตกลงมาเหลือ 0.545** แล้วค่อย ๆ ฟื้นกลับมา **0.909** หลังปรับกราฟให้สมจริง
เส้นทาง **1.000 → 0.545 → 0.909** นี้แหละคือเครื่องพิสูจน์ว่า **เราวัดของจริง ไม่ได้แต่งตัวเลข** —
ตัวเลขที่ตกได้คือตัวเลขที่เชื่อถือได้

---

## 5. ต่อยอดอะไรไปแล้วบ้าง

หลังพิสูจน์แนวคิดหลักได้ เราต่อยอดให้มันเป็นงานวิจัยที่แข็งขึ้น:

1. **ขยายจาก 1 → 4 เหตุการณ์** (แก้ปัญหาข้อมูลน้อย ด้วยการไปขุด Excel ระดับตำบลของ GISTDA มารวมเป็นระดับจังหวัด)
2. **สถิติ 2 ชั้น** — McNemar exact test (จับคู่) + bootstrap CI เพื่อไม่ให้อ้างเกินข้อมูล
3. **ตรวจภูมิประเทศจริง 4 วิธี** — เอาแบบจำลองความสูงพื้นดิน (DEM Copernicus) มายืนยันว่าน้ำไหลตามทิศที่กราฟบอกจริง
   (flow accumulation ผ่าน 11/11, routing 8/11)
4. **ชั้นพยากรณ์/ความเสี่ยง (extension)** — ทำเป็น "ส่วนเสริม" โดยระบุชัดว่า *ค่าที่วัด/ทำนายมาจากอะไร*
   และสำคัญคือ **"ทำไมมันอาจไม่เกิด"** (ความไม่แน่นอน) — ยึดกรอบ Risk = Hazard × Exposure × Vulnerability (UNDRR/IPCC)
5. **Blind test** — โมเดลเรามี **0 พารามิเตอร์ที่เรียนรู้** จึงทดสอบกับเหตุการณ์ที่ไม่เคยเห็นได้ตรง ๆ (held-out F1 0.80–0.94)
6. **ออกแบบ UI ใหม่ 3 หน้า** แยกหน้า user (ถามว่าทำไมท่วม) ออกจากหน้าหลังบ้าน (ดูผลวิจัย)
   + เขียนเอกสาร 2 เล่ม (เชิงเทคนิค + เชิงวิชาการ) เป็นฐานทำ thesis ต่อ

---

## 6. ส่วนพยากรณ์ (Extension B) — ทำอะไร + ค้นพบอะไร

หลังงานหลัก (การให้เหตุผล) แข็งแล้ว เราแยกทำ **ส่วนเสริม: พยากรณ์/เตือนภัยล่วงหน้า** เป็นอีกโมดูล (Thesis B) —
**กลับด้านกราฟ**มาตอบ *"จังหวัดไหน/เมื่อไหร่/โอกาสเท่าไร"* โดยยึดกติกาเหล็ก: **ห้ามแก้โมเดลจากผล (0 learned params)**
เรียนรู้ได้เฉพาะ *ชั้น calibration บาง ๆ* เพื่อ**ไม่ให้ overfit**

**ทำอะไรมาบ้าง:** เก็บ **Case Bank** (ทุกคำเตือนถูก/ผิดเทียบ GISTDA) → **calibrate ความน่าจะเป็นแบบ leave-one-event-out**
→ **วัดผลเต็มรูป** (Brier decomposition · Brier Skill Score เทียบ climatology · ECE · cluster bootstrap · drift)
→ ต่อมา**ปลดล็อกเกจน้ำจริงย้อนหลัง** (thaiwater API) มาสร้าง gate อัตโนมัติ → โชว์ track record ในหน้าเตือนภัย

**ค้นพบอะไร (เล่าให้อาจารย์ฟังได้):**
- **การเตือน (แบบมี/ไม่มีท่วม) แข็งและ generalize** ข้าม 5 เหตุการณ์จริง (CSI 0.80) — จุดอ่อนอยู่ที่ *ความแม่นของความน่าจะเป็น* ไม่ใช่การตัดสินใจเตือน
- **calibrate ตามความลึกของสายเหตุ-ผล (causal-hop) มี skill** เหนือการเดาแบบ climatology — แต่ด้วยแค่ 5 เหตุการณ์ **ยังไม่ significant** (รายงานตรง)
- **จุดที่น่าภูมิใจสุด:** เราสร้าง gate **อัตโนมัติจากเกจน้ำจริง** (ปริมาณน้ำ > ความจุที่สถานีควบคุม เช่น เขื่อนเจ้าพระยา C.13 — อิสระจากภาพดาวเทียมที่เป็นเฉลย) แล้วมัน **ให้ผลตรงกับ gate ที่ผู้เชี่ยวชาญ RID คัดมือเป๊ะ** → พิสูจน์ว่าระบบสร้างเองได้ ตรวจสอบได้ ทำซ้ำได้
- **ความซื่อสัตย์ที่สำคัญ:** พอเพิ่มเหตุการณ์จริงปี 2568 เข้าไป **คะแนน calibration ตกลง** (BSS +0.147→+0.069) — เรา*รายงานตามจริง ไม่ย้อนกลับ* เพราะข้อมูลจริงเผยว่ามันยังไม่ robust (คู่ขนานกับบทเรียน F1 1.000→0.545 ของงานหลัก)
- **ข้อจำกัดที่วินิจฉัยชัด:** ที่พลาด (FN) **9 ใน 11 เป็นลุ่มปิง** ที่ท่วมจาก*ฝนต้นน้ำท้องถิ่น* ไม่ใช่แม่น้ำสายหลักล้น — ยืนยันด้วยเกจจริง (สถานีปิงตอนล่างไม่ล้นจริง) → เป็นข้อจำกัดเชิงกลไก **ไม่ใช่ gate ผิด**

**บรรทัดเดียวสรุป B:** *"ระบบเตือนภัยบนกราฟเหตุ-ผล เตือนได้แม่นระดับตัดสินใจและ calibrate อย่างซื่อสัตย์;
สิ่งที่ยังต้องทำคือจับ 'ฝนต้นน้ำท้องถิ่น' และเพิ่มเหตุการณ์ให้พอ — ไม่ใช่ปัญหาระเบียบวิธี"*

> *"งานนี้ไม่ได้จะบอกว่า GraphRAG ทายน้ำท่วมแม่นกว่า — แต่จะบอกว่า เวลามันตอบ*
> *มัน **อธิบายเหตุผลย้อนกลับไปหาหลักฐานได้ทุกก้าว** ในขณะที่ vector search ตอบได้แต่บอกไม่ได้ว่าทำไม*
